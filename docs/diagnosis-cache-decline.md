# 诊断报告：v4-flash 经 dsh-tap 插件"缓存命中率下降快"根因

日期：2026-09-03 ｜ 环境：dsh 0.1.1-rc.2（web）+ dsh-tap 0.9.1 ｜ 网关：copilot.tencent.com ｜ 对照上游：api.deepseek.com（deepseek-official provider，同模型 id deepseek-v4-flash）
方法：受控探测（直连网关，max\_tokens=16）+ 同日 A/B 会话（官方直连 vs 经桥）+ 桥 DUMP 字节级取证 + dsh 会话日志全量挖掘（84 会话）+ 本地机制复现。
预算遵守：真实网关 chat 调用 47 次（探测 43 次 max\_tokens=16 + 经桥 A/B 会话 4 次，回复按提示约束为单句）；官方 API 调用 5 次；/v2/accounts 账户核验 2 次。实验后 \~/.dsh 文件层已复原（managedProviders=ark、凭据原样、dsh web 无取证 env 重启）。

**原始数据**：探测 JSONL、84 会话逐步 usage 挖掘结果、桥取证日志、DUMP 损坏点分析（不含消息明文）均为开发期原始证据，未纳入开源快照；本文结论与机制签名自包含。

## TL;DR（多因按贡献排序）

1. **主因（贡献压倒性，插件侧缺陷）：桥的请求体逐分片解码损坏出站前缀。** `core/bridge.js` 的 `listen()` 用 `rawBody += c`（c 是 Buffer → 逐 TCP 分片隐式 utf8 解码）组装入站请求体：跨分片边界的多字节中文字符被替换成 3×U+FFFD，且分片边界逐请求随机 → 出站体**前缀逐请求漂移** → 网关按内容寻址的前缀缓存只能命中到"本次损坏点"为止。上下文越大（分片边界越多）、中文密度越高（注入的 AGENTS.md/中文网页内容），单请求损坏概率越高——这就是"命中率随会话变长下降快"的形状来源。**网关本身无罪**：直连网关的受控探测在 16k/32k 同 prompt 连发 24 发全 99.3%、条目无刷新存活 600s；dsh 存储层 0 个 U+FFFD（损坏发生在桥的组装，不在发送侧）；本地 mock 复现逐字吻合现场签名。
2. **次因（对照口径）：两侧上游本就不同。** 官方 API 与 CodeBuddy 网关是两套缓存基础设施——但本案实测**网关缓存行为良好**（见 §3 基线），"上游差异"不是命中率差距的解释；真正拉开差距的是官方路径不经桥、无前缀损坏。
3. **无关项（全部证伪）**：多 Key 轮换（OAuth 单凭据，结构上无轮换）、凭据类别（ck\_/OAuth 同账户同行为）、指标口径（hit+miss==prompt 逐行成立、桥计量与 dsh 记录逐数相等）、网关短 TTL（600s 不失效）、会话行为模式（同脚本官方侧 97-99%）。

一句话：**"下降快"不是网关缓存差，是桥把发给网关的请求体弄脏了——每个请求脏在随机位置，内容寻址缓存忠实地把"脏点"当缓存边界。**

***

## 1. 现象定形

- 用户场景：authMode=oauth（另有 1 把 ck\_ Key 备用）、`sessionHeadersEnabled` 默认 true（但 dsh 出站无会话 id，桥实际不注入会话头）、主聊天经 :3901 桥。

- 统一指标：每请求 `usage.prompt_cache_hit_tokens / prompt_tokens`（网关 SSE 自报，经桥计量与 dsh 会话记录双源一致，§5 H5）。

- 现象（历史会话挖掘，codebuddy/deepseek-v4-flash 13 个多步会话）：聚合命中率 0–96.2% 剧烈波动；轮内步骤 p50=97% 但 **11.0% 的步骤 <60%**（塌落值吸附 128 倍数"快照"）；10–60s 空闲后的轮首中位数 **1%**（19 例中 9 例全 miss）。对照 deepseek-official/deepseek-v4-flash 9 个多步会话：聚合 80.8–98.2%（多为 94–98%，最大 171k 上下文），轮内 <60% 仅 1.2%，轮首在 5–30min 空闲后仍 99%。

## 2. 根因证据链：桥逐分片解码损坏

### 2.1 现场捕获（2026-09-03 E6，经桥真实会话）

同脚本两会话（Q1=读 package.json 的 name、Q2=追问），唯一差异是 provider：

| 步骤          | 官方直连（E7，session-aa162372） | 经桥网关（E6，session-2584c54c） |
| ----------- | ------------------------- | ------------------------- |
| t1s1（冷启动）   | 0%（16885 tok）             | 0%（16745 tok）             |
| t1s2（+2.4s） | **97.2%**                 | **39.4%**（hit 6912）       |
| t2s1（+7s）   | **99.4%**                 | **71.6%**（hit 12672）      |

E6 开 `CODEBUDDY_BRIDGE_DUMP` 抓到 3 个 chat 请求体（75–78kB）。字节级比对：

- t1s1：全干净（0 个 U+FFFD）。

- t1s2：消息\[2]（注入的本仓 AGENTS.md 工作区规则，13.1kB 中文密集）在字符 4675 处的 `）` 变成 3×U+FFFD（长度 +2 字符）。

- t2s1：字符 4675 处**复原**，字符 10581 处**新损坏**——损坏位置逐请求随机游走。

- 连续请求共享前导消息仅 2/N（系统提示 + 首条 user）；tools 数组逐字节相等（33 个工具，35671B 恒定）。

### 2.2 命中值 = 损坏点（定量对应）

| 请求对                | 请求体字节级公共前缀 | 网关实测 hit              | 说明                                      |
| ------------------ | ---------- | --------------------- | --------------------------------------- |
| t1s2 vs t1s1（干净条目） | 23899B     | 6912 tok（3.46 B/tok）  | 分叉点=损坏位置 4675                           |
| t2s1 vs t1s1（干净条目） | 32586B     | 12672 tok（2.57 B/tok） | 分叉点=损坏位置 10581；两段 B/tok 差异恰由中间区域的中文密度解释 |

网关把"最长干净前缀"如实命中（t2s1 命中的是更早的干净条目 t1s1 而非上一请求 t1s2）——**缓存逻辑完全正确，是请求在变**。

### 2.3 发送侧清白 + 机制本地复现

- dsh 会话存储层（session.jsonl.zstd）对同一请求 **0 个 U+FFFD**（含 E6/E7/09-02 三个会话）——dsh 序列化干净，损坏发生在桥的收包组装。

- 本地 mock 复现（tmp-repro，同 `rawBody += c` 模式的服务器 + 原生 socket 分片写入）：`）`（E3 80 89）跨 2 个或 3 个分片 → **恰好 3×U+FFFD、字符串 +2 字符**，与现场签名逐字一致；单次写完整块则完好。

### 2.4 历史数据全部重释（此前归因于"网关保留不稳"的现象）

| 历史观察（旧归因）                                               | 重释（桥损坏断点）                                                                                 |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------- |

| 09-02 会话 hit 4352/5504（"只剩系统提示"）                        | 损坏点落在消息\[2]极早处（系统提示 4352 tok 恰为英文、单段、极少被分片切断）                                             |

### 2.5 波及面（同模式 3 处）

`grep` 全仓库，同 `body += chunk`（Buffer 隐式逐块 utf8 解码）模式共 3 处：

- `core/bridge.js:492-495`——主聊天桥（本案根因）

- `providers/trae/gateway.js:677-682`——Trae 翻译网关 :3902（同缺陷：入站解析已损坏，译文带 FFFD 上行）

- `index.js:918-921`——设置路由（体量小、单分片为主，但 provider displayName 等含中文，同类风险）

附带影响（超出缓存）：**模型收到的上下文本身带 FFFD 乱码**——每请求若干中文字符损坏，是正确性缺陷而不只是计费问题。

## 3. 衰减曲线（三维度）与网关侧理想基线

**基线（直连网关、合成英文 payload、无桥）**——网关缓存的"应然"行为：

- burst（E2）：16k 同 prompt，ck\_/OAuth 交错各 12 发 + seed → **24 发全部 99.3%（hit 14976/15088），零塌落**

- TTL（E3）：16k 与 32k 各一臂，条目无刷新间隔 30/120/600s → **全部 99.2%/99.8%**（v4-flash 网关 TTL ≥ 600s，无短时失效）

- grow（E4）：16k 起每步 +1.5k 共 8 步（3s 间隔）→ 92–94%（命中=上一步前缀 floor，属正常增长形态）；60s 空闲后增长读取 → **94.5% 全命中**；仅 1 步瞬时回退一档后自愈

**轮次/长度维度（真实会话，挖掘 84 会话）**：插件路径轮内步骤 p10=56%、<60% 占比 11.0%；塌落频率随上下文规模与中文密度上升（f52c817f avg 55.5k → \~65% 步骤受损；≤20k 多数会话健康）。官方路径 p10=89%、<60% 占比 1.2%，171k 上下文仍 97%。

**间隔维度（真实会话轮首统计）**：

| 空闲间隔    | 网关经桥（中位数/全 miss 数） | 官方直连（中位数）         |
| ------- | ------------------ | ----------------- |
| <10s    | 98% / 0            | 98%               |
| 10–60s  | **1% / 9 例全 miss** | 99%               |
| 1–5min  | 0% / 4 例全 miss     | 98%               |
| 5–30min | 98% / 1 例          | 99%               |
| >30min  | 0% / 6 例           | 0%（官方 TTL 到期，1 例） |

经桥侧的非单调形状（5–30min 反而 98%）与 TTL 模型矛盾、与"逐请求随机损坏"模型吻合（轮首全 miss 通常是：上一请求已损坏 + 本请求又损坏在不同位置 → 命中跌到更早的干净条目以下）。

## 6. 修复建议（按任务纪律：只定位，不实施）

1. **主修（一行级）**：`core/bridge.js` listen() 改为 Buffer 收集 + 一次解码——`const chunks=[]; req.on('data',c=>chunks.push(c)); req.on('end',()=>{ const rawBody=Buffer.concat(chunks).toString('utf8'); … })`。32MB 上限判断改用累计字节数。**预估收益**：消除逐请求前缀漂移，插件路径命中率回到基线形态（轮内 ≈92–99%、短空闲轮首全命中、TTL ≥600s），与官方路径的差距坍缩到网关 per-model 策略本身；同时消除发给模型的 FFFD 乱码。
2. **同型修复**：`providers/trae/gateway.js` listen() 与 `index.js` 设置路由的 `raw += c` 同改（Trae 通道当前未启用，但代码在；设置路由体量小风险低）。
3. **回归锁**：verify-bridge 增加"多分片中文体完好性"用例（mock 上游 + 分片写入断言 bodySha 与整块发送一致）——现有 mock 测试全用单块写Body，正是本坑漏网 8 个版本的原因。
4. 非修复项：网关侧无可修项（其缓存行为正确）；"请求指纹→会话映射"仍无收益（R-C1）。

## 7. 不可观测边界（诚实声明）

- 分片边界的分布（何时/何处切断）取决于本机 TCP 收包时序，客户端只能统计频率、不能预测位置。

- 网关内部对多份前缀变体的条目共存/淘汰策略不可观测（本案不需要它——最长干净前缀命中已足以解释全部数据）。

- 多 Key 场景的缓存命名空间是否按凭据隔离未测（需第二账户凭据）。

- 历史会话无法逐个重放确认损坏点（DUMP 是本轮才开）；重释基于机制签名的完全吻合（3×FFFD、位置游走、hit=断点、ASCII/CTS 密度与体量的相关性）。
